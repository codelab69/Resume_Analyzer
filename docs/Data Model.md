# Data Model

Two tables in one SQLite file. The interesting part of this note is not the schema —
it is the list of things deliberately **not** stored.

---

## What is not stored, and why that is the important half

> [!important] The original file never reaches the disk
> An uploaded resume is read from the request into memory, analysed, and dropped. Only
> the **extracted text** is persisted, inside the report.
>
> The PDF itself carries a full name, a phone number, an email address, often a home
> address, and an academic record. Not writing it anywhere means there is no directory
> of other people's resumes to secure, back up by accident, commit by accident, or
> forget to clear out after the project is marked.

This is enforced by a test, not just asserted here —
`TestPersonalDataIsNotWrittenToDisk` in `backend/tests/test_api.py` uploads a resume and
fails if any file appears beside the database.

| Not stored | Why |
|---|---|
| The uploaded file | See above. Nothing needs the bytes after extraction |
| Accounts, emails, sessions | The tool is anonymous. There is no user to attach a resume to, so there is nothing to accumulate |
| IP addresses or analytics | Nothing about who uploaded what |
| Anything at all after `DELETE` | The cascade is real — see [[#3. Deletion actually deletes]] |

> [!note] A setting that described storage which never happened
> `UPLOAD_DIR` used to exist. It was documented in `.env.example` and the README as
> *"where uploaded resumes are written"*, and **nothing ever wrote to it**.
>
> That is worse than either alternative. Anyone auditing how this project handles
> personal data — a reviewer, a placement officer, a examiner — would have read the
> config and been told something false. It has been removed rather than implemented,
> because not storing the file is the better behaviour and the honest thing is to say
> so plainly. `test_there_is_no_upload_directory_setting` stops it coming back quietly.

## The schema

`backend/app/store.py`. Plain SQL, standard-library `sqlite3`, no ORM.

```sql
CREATE TABLE resumes (
    id           TEXT PRIMARY KEY,
    file_hash    TEXT NOT NULL UNIQUE,   -- SHA-256 of the file bytes; the cache key
    filename     TEXT NOT NULL,
    ats_score    INTEGER NOT NULL,
    role         TEXT,
    skill_count  INTEGER NOT NULL DEFAULT 0,
    created_at   TEXT NOT NULL,
    payload      TEXT NOT NULL           -- the full report, as JSON
);
CREATE INDEX idx_resumes_created ON resumes (created_at DESC);

CREATE TABLE matches (
    id           TEXT PRIMARY KEY,
    resume_id    TEXT NOT NULL,
    job_title    TEXT,
    score        INTEGER NOT NULL,
    created_at   TEXT NOT NULL,
    payload      TEXT NOT NULL,
    FOREIGN KEY (resume_id) REFERENCES resumes (id) ON DELETE CASCADE
);
CREATE INDEX idx_matches_resume ON matches (resume_id, created_at DESC);
```

## Four decisions worth explaining

### 1. The report is a JSON column

`payload` holds the entire report. Only the fields actually **queried on** are promoted
to real columns: `ats_score`, `role`, `skill_count` and the timestamps, all of which the
dashboard aggregates over.

The report shape is still changing. A JSON column absorbs a new field without a
migration; a fully normalised schema would mean a migration every time a rule gains an
explanation string. The rule of thumb: *promote a field to a column the moment you want
to filter or sort by it, and not before.*

The cost is honest — you cannot query inside `payload` efficiently. If the dashboard
ever needs "every resume that mentions Kubernetes", that is the point at which skills
become their own table.

### 2. `file_hash` is UNIQUE, and that is the caching strategy

Re-uploading a byte-identical file returns the existing `id` instead of analysing again
or creating a second row.

`save_resume()` returns the existing id rather than raising on a conflict, so the caller
never has to check first — which would be a race anyway. **The returned id is
authoritative:** if it differs from the id the caller proposed, another request stored
the same file first and the caller must use the returned one.

The id is chosen by the caller rather than generated by the insert, because the stored
payload embeds its own id. One write, no patching.

For a placement cell running sessions, this also means twenty students uploading the
same college resume template produce one row, not twenty.

### 3. Deletion actually deletes

```sql
FOREIGN KEY (resume_id) REFERENCES resumes (id) ON DELETE CASCADE
```

> [!warning] SQLite ignores this clause by default
> Foreign key enforcement in SQLite is **off unless switched on per connection**.
> `_connect()` issues `PRAGMA foreign_keys = ON` for exactly this reason.
>
> Without it, the clause above is decorative: deleting a resume would leave its match
> history behind, still linked to a row that no longer exists. "Deleted" would be a lie
> — and it is a lie told to a student, in person, at the end of a testing session, on
> the strength of the promise in [[Customer Testing Plan#Consent and privacy]].
>
> `test_deleting_a_resume_removes_its_match_history_too` asserts the history is
> genuinely empty afterwards, and `e2e_check.py` re-checks it over real HTTP.

### 4. Timestamps are TEXT

ISO-8601 strings in UTC. SQLite has no date type, and ISO-8601 sorts correctly as text,
which is all `ORDER BY created_at DESC` needs. Storing an integer epoch would be
marginally smaller and considerably less readable when someone opens the file in a
database browser to see what went wrong.

## Indexes, and what they are for

| Index | The query it exists for |
|---|---|
| `idx_resumes_created` | The dashboard lists newest first. Without it, every page load is a full scan plus a sort |
| `idx_matches_resume` | `GET /api/match/history/{resume_id}` — filters by resume, orders by date. The composite covers both |

`file_hash` needs no separate index: `UNIQUE` creates one.

At 26 postings and a classroom's worth of resumes, none of this is load-bearing. They
are here because the queries are obviously indexable and adding them later means
noticing the problem first.

## Moving to Postgres

Every statement in `store.py` is plain SQL against two tables, and **nothing outside
that file writes SQL**. That is the entire reason the storage layer is one module.

To move:

1. `_connect()` returns a psycopg connection instead of a `sqlite3` one.
2. `?` placeholders become `%s`.
3. `TEXT` primary keys become `uuid`, and `payload` becomes `jsonb` — which gets you
   queryable JSON, removing the main cost noted in decision 1.
4. Drop the `PRAGMA`; Postgres enforces foreign keys without being asked.

Nothing in `app/core`, `app/api` or the frontend changes.

## Operational notes

**The database file is `backend/storage/app.db`**, created on first run, and
git-ignored — see the reasoning at the top of `.gitignore`.

**To wipe everything between testing sessions**, stop the server and delete the file.
It is recreated empty on next boot. This is the blunt version of the per-resume delete,
and it is the right thing to run after a day of sessions with real students.

**There are no migrations.** `init_db()` runs `CREATE TABLE IF NOT EXISTS` at startup.
Adding a column to an existing database means either adding it to the JSON payload
(usually correct) or deleting the file and starting again (acceptable for a project at
this stage, and worth revisiting the moment real data needs preserving).
